# 行程一页纸 TripOnePager · PRD

> 版本 v1.0 ｜ 2026-11-06 ｜ 作者：Aurorawby（AI 结对编程）
> 一句话：**把收藏夹里乱糟糟的旅行攻略变成可执行、可打印带走的一页行程——代码解析结构、诊断排太满漏吃饭，AI 只做自由文本抽取。**

---

## 1. 背景与问题

旅行前最乱的环节不是订票，是**攻略整理**：

- 收藏了 5-8 篇小红书/公众号攻略，出发那天要来回翻；
- 攻略是「种草清单」不是「时间表」——哪天去哪、中午在哪吃、门票预约没约，全靠脑子拼；
- 最常见的行程崩坏：一天排 5 个景点跑断腿、某天忘了安排吃饭、住宿没定导致每天横穿城市。

**机会**：这些是**结构问题**，结构问题可以代码化——解析（条目/天数/花费）→ 诊断（排太满/漏吃饭/超天数）→ 渲染（一页时间线）。
与文献综述 Agent、汇报一页纸是同一套「解析 → 诊断 → 渲染」方法论的第三次迁移。

## 2. 目标用户与场景

| 谁 | 场景 | 频率 |
|---|---|---|
| 自由行旅行者 | 出发前 1-3 天：粘贴收藏的攻略 → 生成一页 → 打印或存图 | 每次出行 |
| 帮家人安排行程的人 | 把爸妈口述的「想去 A、想吃 B」整理成一页 | 节假日 |

## 3. 产品目标与指标

**北极星**：从粘贴攻略到可打印一页 ≤ 2 分钟（结构化文本走规则解析 10 秒；乱文本走 AI 抽取 1 分钟）。
**正确性护栏（可测试）**：解析（天数 / 条目 / 类型 / 花费）与诊断触发与手工判定一致（确定性回归）。
**信任指标**：AI 抽取后用户核对率——页面持续提示「模型可能漏抽错抽，出发前核对门票与营业时间」。

## 4. 需求清单

| 级别 | 需求 | 验收标准（可测试） |
|---|---|---|
| P0 | 攻略解析：Day/第N天分隔、📍/序号/符号条目、「门票/人均/营业/住宿」副信息挂靠、类型分类（景点/餐/住宿/交通/其他） | 块结构（天数 / 条目数 / 类型 / 花费）与手工标注一致（回归评测） |
| P0 | 结构诊断：单日景点 ≥4（偏满）、单日无餐（漏吃饭，⛔）、多日无住宿、攻略天数超出设定 | 触发与手工判定一致 |
| P0 | 一页渲染：按天分组时间线、类型图标、每条花费、每日/总花费合计 | 渲染含全部条目与合计 |
| P0 | 打印导出：@media print 只输出一页行程 | 打印预览仅含行程 |
| P1 | AI 自由文本抽取：乱格式攻略 → 结构化 POI JSON（type 白名单校验、字段截断） | 抽取后仍走代码诊断；解析失败展示错误不崩溃 |
| P1 | 演示攻略：北京 2 日（含 Day2 排 4 景点的「偏满」样本） | 装载即触发诊断 |
| P2 | 地理聚类提示（同区域条目归并到同一天） | 需要地理编码，M2 评估 |
| P2 | 天气/营业时间核查 | 依赖外部数据源，M2 评估 |

## 5. 明确不做（Not-doing）

- **不做实时数据**（门票余量 / 营业时间 / 天气）：依赖外部 API 与维护成本，页面明示「出发前请核对」；
- **不做导航 / 路线规划**：地图App 的本职，不做重复的差产品；
- **不做多人协作行程**：单机单页，协作是文档平台的事；
- **AI 抽取不替代人工核对**：模型可能漏抽错抽，页面持续提示对照原文。

## 6. 关键设计决策

1. **规则解析优先、AI 兜底**：结构化攻略（有 Day 标记和条目符号）走确定性解析（快、免费、可测）；
   自由文本才交给 AI 抽取，且抽取结果**必须再过代码诊断**——AI 产出不直接可信；
2. **诊断是产品核心**：「排太满 / 漏吃饭」是行程崩坏的两大根因，把旅行老手的经验做成规则；
3. **副信息挂靠**：「门票 60 元」「人均 150」这类短行自动归到上一个条目——攻略的自然写法就是条目+注释；
4. **一页 + 打印**：旅途中手机看收藏夹会断网/分心，纸质一页是最可靠的离线载体（与汇报一页纸同哲学）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 攻略写法千奇百怪，解析认不全 | 认不全的行进条目或忽略，不丢「已识别」内容；AI 抽取兜底；PRD 列明支持的格式 |
| AI 抽取漏抽 / 错抽 | 白名单校验 type、字段截断；结果必须过代码诊断；页面持续提示人工核对 |
| 诊断误报（有人就爱排满） | 文案用「建议砍掉或挪动」语气；阈值（≥4 景点）是舒适度经验值，PRD 写明 |
| 类型误分类（如「什刹海」不匹配任何关键词） | 归入「其他」不丢弃，图标兜底；词典随迭代扩充 |

## 9. 里程碑

- **M1（已完成，本版本）**：P0 全部 + P1 全部 + 确定性回归评测；
- **M2**：地理聚类（同区域归并）、多攻略合并去重、第二人标注解析口径。

## 10. 本 PRD 的局限

- 解析器支持的攻略格式有限（表格 / 图片型攻略不支持——图片需 OCR，超出单文件产品范围）；
- 类型词典覆盖常见 POI 词根，新词根会进「其他」；
- 花费合计只累加文本中显式标价的条目，无价格条目不计入（不估算）；
- 诊断阈值（≥4 景点偏满）是通用经验，带老人小孩的节奏应更松。

## 竞品分析（2026-11-06 补充）

> 口径：基于公开产品能力的定性对比，未做付费/深度评测。

| 替代方案 | 它强在哪 | 在我们场景里的不足 | 我们的差异 |
|---|---|---|---|
| 小红书/马蜂窝攻略 | 真实体验、图片多、社区强 | 信息密度低，不能变成可执行日程，也不会提醒「排太满/漏吃饭」 | 粘贴攻略 → 解析 → 诊断 → 打印一页 |
| Notion / Excel 行程表 | 自由、可协作 | 要手工录入和排版，诊断靠人 | 自动解析 Day/POI/花费，结构诊断代码化 |
| 行程类 App | 机酒预订、地图成熟 | 不解决「别人攻略怎么变成我的行程」 | 不抢预订，只做攻略到一页纸的转换 |

**结论：** 不是旅行 App，是「攻略 → 可执行行程」的解析/诊断/渲染小工具。
