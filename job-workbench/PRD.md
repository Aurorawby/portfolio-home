# 求职工作台 · PRD

## 1. 背景

三个求职工具已经各自能用：JD 雷达（看市场要什么）、模拟面试官（生成题）、面试复盘器（面完复盘）。
但真实求职是**连续流程**，分开用有三个摩擦：

1. **重复输入**：同一份 JD 要在三个页面各粘一次，简历要粘两次；
2. **结论散落**：雷达的 gap、生成的题、复盘出的薄弱项分别在三个页面，面试前要翻三处；
3. **不知道下一步**：做完一步后，不清楚该去哪个工具、还差什么。

这三个摩擦不解决，三个工具就只是"三个 demo"，不是"一条求职流程"。

## 2. 目标用户

正在求职的 AI 产品岗候选人（我自己 + 同学）。

## 3. 目标与非目标

**目标**

1. 一页看清三步进度（JD 扫描 / 生成题 / 复盘）；
2. **输入一次，三个工具共用**；
3. 自动汇总成一份「求职档案」（Markdown），面试前 10 分钟能过一遍；
4. 预测面试题能一键带入复盘器。

**非目标**

- 不重写三个工具的逻辑（避免三个页面代码合并成一个巨型页面）；
- 不做账号/云端同步（求职数据留在本机更安全）；
- 不做面试日历/提醒（下一步再说）。

## 4. 方案：编排层，不是第四个工具

| 层 | 归属 | 职责 |
|---|---|---|
| 能力词典 / 雷达 | JD 雷达页面 | 分析 JD，写 `jd_last` 摘要 |
| 题库 / 生成 | 模拟面试官页面 | 生成题，写 `mock_interview_state_v1` |
| 复盘编辑 | 面试复盘器页面 | 记录真实问题，写 `ir_state` |
| **编排 + 汇总** | **工作台** | 读写共享 localStorage，展示进度，生成档案 |

**共享键**：`jwb_state`（JD/简历）、`jd_last`、`mock_interview_state_v1`、`ir_state`。
工作台只做三件事：读、汇总、写回（带入）。

这样每个工具仍然可以单独使用，工作台只是一个"主线入口 + 汇总器"，**不重复实现逻辑**。

## 5. 关键交互

1. 工作台填 JD + 简历 → 点「保存并带给工具」→ 一键写入三个工具需要的键；
2. 点「去扫描 JD」→ JD 雷达自动带出 JD → 分析后写 `jd_last`；
3. 点「去生成面试题」→ 模拟面试官自动带出 JD + 简历；
4. 点「把预测题带入复盘」→ 合并进复盘器（按题目去重），类型先标「待分类」；
5. 回到工作台刷新 → 三步状态 + 汇总数字更新；
6. 导出 / 复制「求职档案」。

## 6. 指标设计

| 层级 | 指标 | 怎么衡量 |
|---|---|---|
| 流程 | 三步完成率 | 三步都完成的用户 / 打开工作台的用户（需埋点，暂本地统计） |
| 效率 | 重复输入次数 | 目标降为 **0**（一次输入，三处复用） |
| 产出 | 档案导出/复制率 | 导出按钮点击 / 完成三步的用户 |
| 质量 | 集成测试 | `node eval/job-workbench/run.mjs` 验证数据流 |

## 7. 风险与边界

- 数据只在**同一浏览器同源**下共享；换浏览器/清缓存会丢；
- 「清空本地数据」会同时清掉三个工具的数据，需要二次确认；
- 带入复盘器的题型是「待分类」，需要用户自己改；
- 工作台本身不产生内容，价值来自三个工具——所以三个工具的质量决定上限。

## 8. 下一步

- 本地埋点：记录三步完成率、导出率（纯前端，存 localStorage）；
- 面试日历：把已安排的面试时间存本地，提前提醒"该复习了"；
- 档案导出 PDF 一页版（面试前打印）。

## 竞品分析（2026-11 补充）

> 口径：基于公开产品能力的定性对比，未做付费/深度评测。

| 替代方案 | 它强在哪 | 在我们场景里的不足 | 我们的差异 |
|---|---|---|---|
| Notion / 飞书模板 | 模板成熟、协作强、多端同步 | JD、面试题、复盘分在不同页面，数据不互通 | 一条线：一次输入 JD + 简历，三步共享状态，最后导出档案 |
| 牛客 / 实习僧 | 岗位多、投递方便 | 不做能力 gap、模拟面试和面后复盘 | 串联 JD 雷达 → 模拟面试官 → 面试复盘器 |
| Excel / 表格 | 自由、门槛低 | 统计和提醒靠公式，跨工具复制粘贴 | 进度自动点亮、档案自动汇总 |

### 本产品的局限

- 只是编排层，不替代三个单工具的能力；
- 跨工具数据靠 localStorage，换设备/清缓存会丢，没有账号体系；
- 没有多人协作，不能替代团队投递管理。

**结论：** 做“流程编排”，不是第四个工具；价值在减少重复输入和断点。

## 经历深挖模块（2026-11-07）

### 背景

简历里一行“负责公众号运营”，面试官追问“你具体做了什么、结果多少”时，候选人往往答不出细节。
这不是“不会面试”，是**经历没有被结构化**：背景、动作、难点、结果、反思散落在记忆里。

### 模块目标

用 5 个问题把一段实习/项目聊成 STAR 故事，输出：
- STAR 结构；
- 30 秒 / 90 秒面试版本；
- 面试官可能追问；
- 需要补的证据（没有数字就标“待补”，不编）；
- 改写建议（弱动词、个人贡献、岗位关联）。

### 用户流程

1. 从工作台带入简历/JD（或手动填）；
2. 5 个问题：背景与目标 → 你做了什么 → 难点与冲突 → 结果与证据 → 反思与迁移；
3. 每答一题，规则层给一条具体反馈（缺数字/弱动词/“我们”太多）；
4. 生成故事，下载 Markdown；AI 润色可选（BYOK，禁止改事实/加数字）。

### 关键设计决策

- **不调用模型也能用**：离线 5 问 + 规则反馈 + STAR 模板；AI 只做可选润色；
- **不编数字**：没有结果数字时输出“待补”，并在“需要补的证据”里提示；
- **保留原文**：报告附原始回答，方便本人核对；
- **不做自动投递/自动发消息**：平台规则与品牌风险。

### 指标（待真实用户测试）

- 完成率：开始深挖 → 生成故事；
- 首次价值时间：从开始到看到 30 秒版本；
- 故事可用率：用户是否愿意复制/下载；
- 待补项数量：越少说明经历越完整（但不能为了少而编）。

### 风险

- 用户可能把 AI 生成的措辞当成事实；页面常驻“必须核对”提示；
- 故事模板可能让所有人听起来一样；因此保留原始回答 + 个人贡献检查；
- 没有真实用户前，不宣称“面试通过率提升”。

### 经历库（2026-11-07 补充）

- 深挖后的故事可一键保存到 `em_library_v1`，按 `title|period` 去重更新；
- 经历库自动汇总：30 秒版、STAR、追问、待补、能力标签、目标 JD 覆盖；
- 能力标签 / JD 覆盖是**规则匹配**，不是语义判断；没有故事/证据时显示“待补”；
- 支持导出 Markdown 故事库；数据仍只在本机。
