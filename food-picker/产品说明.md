# 吃什么决策器 · 产品说明（作品集版）

> 一句话：**「今天吃什么」的解法不是推荐算法，是把 PM 的多准则决策矩阵做成 30 秒能用的工具：候选打分 → 硬约束过滤 → 调权重 → 加权排序，纠结到底就交给天意（约束内随机 + 承诺机制）。**

---

## 1. 为什么做

「今天吃什么」是全球最高频的决策难题。它的痛苦不是没有选项，是**选项没有结构**：
好吃和顺路不在同一个维度比，忌口和预算总在最后才想起。

解法是产品经理每天都在用的**多准则决策矩阵**：候选打分 → 硬约束过滤 → 加权排序 → 结果可解释。
把它做成工具，顺便让「权重」「硬约束 vs 软偏好」「tie-break」这些决策概念变得可触摸——
这也是我做这个产品的另一半动机：**决策方法论的产品化实验**。

## 2. 我做成了什么

| 模块 | 实现 |
|---|---|
| 候选管理 | 名称/人均/四维主观分（想吃·顺路·预算合·不排队 1-5）/忌口标签，localStorage 持久化 |
| 硬约束过滤 | 预算上限、忌口标签（子串匹配）、顺路下限；**被拒候选连原因一起展示** |
| 加权排序 | 四维权重滑条归一化加权；并列固定 tie-break（不排队优先），结果可复现 |
| 结果卡 | winner + 四维条形拆解 +「为什么是它」（最强维度/相对短板） |
| 天意模式 | 约束内等权随机 +「不许再刷」承诺文案——决策终止机制 |
| AI 点菜（可选） | 按人数/预算/忌口生成点菜清单（JSON 容错，建议仅供参考） |
| 演示候选 | 6 家含超预算/含忌口样本，装载即见过滤效果 |

## 3. 验证（可复现）

`node eval/food-picker/run.mjs`（不调用模型、不依赖浏览器）：

| 检查 | 结果 |
|---|---|
| 硬约束过滤（预算 / 忌口 / 被拒原因） | 与手工判定一致 |
| 加权排序（6 家候选、总分 4.25/4.13/3.88 逐项核对） | 一致 |
| tie-break 与并列次序 | 一致 |
| 全被筛掉时的空结果处理 | 一致 |

**诚实口径**：确定性回归测试；天意模式是随机过程，不进回归（非确定过程无法断言）；
评分是用户主观输入，工具的价值是结构化对比，不是替你了解口味。

## 4. 关键取舍

1. **透明矩阵而不是推荐算法**：用户看到「你的分数 × 你的权重 = 你的排序」——不黑盒、可解释、改权重结论会变；
2. **硬约束先于软偏好**：忌口/预算是一票否决，不混进打分——「绝对不能接受」和「稍微差点」是两种决策；
3. **tie-break 固定**：并列必须确定，否则结果不可复现、评测无从断言；
4. **天意模式是正经功能**：决策疲劳的解法之一是「随机化 + 承诺」——信息不足以区分时，随机就是最优解。

## 5. 边界

- 候选来自用户自己的清单，工具不验证真伪（垃圾进垃圾出，页面明示）；
- 忌口是子串匹配：「辣」会匹配「微辣」也可能匹配「不辣」——标签粒度由用户自己控制；
- 天意模式的随机性导致其结果不可复现（设计如此）；
- 单人打分；群体模式（多人打分取均值）在 M2。

## 6. 如果继续做

- 历史回流：吃过之后记录满意度，喂回「想吃度」基线（与内容工作台的数据回流同理念）；
- 群体模式：多人各自打分取均值，忌口取交集；
- 排除语义标签（「不辣」显式排除）。
