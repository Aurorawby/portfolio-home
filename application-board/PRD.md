# 投递看板 ApplicationBoard · PRD

> 版本 v1.0 ｜ 2026-11-03 ｜ 作者：Aurorawby（AI 结对编程）
> 一句话：**把每一次实习 / 秋招投递记进看板——漏斗、渠道、死因、跟进提醒全部由代码现算，AI 只做复盘文案。**

---

## 1. 背景与问题

投递季的真实状态是「一团浆糊」：

- 投了 40 家，被问「走到哪了」只能翻聊天记录和邮箱；
- Excel 模板能记账，但**不算数**：不会告诉你投递→面试转化率是多少、哪个渠道在浪费时间、哪家已经 20 天没下文该放下；
- 挂了就挂了，**没有死因记录**——同一个坑掉三次。

**机会**：投递是一个天然漏斗（投递→笔试→面试→Offer）。把漏斗做进工具，统计就是免费的；
把「死因」做成必填字段，复盘就有抓手。

## 2. 目标用户与场景

| 谁 | 场景 | 频率 |
|---|---|---|
| 实习 / 秋招求职者（含我自己） | 每次投递 / 收到笔试面试 → 记一条改状态；每周日看一次漏斗和渠道效果，决定下周投哪里 | 投递期每天 1 分钟 |
| 有内推资源的同学 | 看渠道进面率，把精力压到进面率高的渠道 | 每周 |
| 挂了很多的人 | 看死因分布 → 高频死因 = 下一轮要补的洞 → 配合「模拟面试官」练 | 复盘时 |

## 3. 产品目标与指标

**北极星**：每周一次「打开 → 看清本周该跟进谁、下周投哪个渠道」的决策 ≤ 3 分钟。
**正确性护栏（可测试）**：漏斗 / 渠道 / 死因 / 提醒四组统计与手工计算完全一致（回归评测 100%）。
**行为指标**（M2，需本地埋点）：记录的「死因填写率」≥ 70%——没有死因的复盘是空的。

## 4. 需求清单

| 级别 | 需求 | 验收标准（可测试） |
|---|---|---|
| P0 | 投递记录 CRUD：公司/岗位/渠道/日期/状态/薪资/死因/备注 | 公司岗位必填；保存后看板即时刷新；刷新页面不丢 |
| P0 | 看板视图：8 状态列 + 卡片流转 | 主流程「下一阶段 / 上一阶段」按钮流转并更新 updated 日期；挂了时引导补死因 |
| P0 | 漏斗统计：各阶段到达数 + 简历过率 / 总 Offer 率 | 与手工计算一致（回归评测断言通过） |
| P0 | 跟进提醒：流程中停 >7 天、已投递 >14 天无下文 | 触发对象与手工标注一致（回归评测断言通过）；天数从 updated（无则 date）起算 |
| P0 | 渠道进面率 + 死因分布 | 进面 = 到过面试及以后或非简历关死亡；死因降序排列 |
| P0 | 导出：复制 / 下载 Markdown 汇总 | 含漏斗、渠道、全量记录表、死因分布 |
| P1 | AI 复盘建议：挂掉的投递给 3 条可执行改进建议 | 输入含死因与备注；输出 JSON 解析失败时展示错误不崩溃 |
| P1 | AI 跟进话术：卡住的流程生成 ≤80 字礼貌跟进消息 | 输入含公司、岗位、停滞天数；同样 JSON 容错 |
| P1 | 演示数据：9 条覆盖全部状态，日期相对今天生成 | 任意时候装载，漏斗 / 提醒立即有内容 |
| P2 | 与「面试复盘器」打通：面试卡片一键带去复盘 | 等两个工具都有真实用户后再做 |
| P2 | 日历视图（面试时间提醒） | 单机通知能力有限，先不做假承诺 |

## 5. 明确不做（Not-doing）

- **不抓投递平台数据**：不做爬虫 / 平台 API 对接（合规风险 + 维护成本），记录手动维护——本来就是 1 分钟的事；
- **不做「投递就成功」的玄学指标**：只报告转化事实，不预测「你能不能拿 offer」；
- **不做云同步 / 多人协作**：求职数据是敏感个人信息，留在本机是特性不是缺陷；
- **阈值不做配置**（M1）：14 天 / 7 天是行业常见节奏的经验值，等有用户反馈说不对再开放。

## 6. 关键设计决策

1. **统计全部代码算，AI 只写文案**：漏斗 / 渠道 / 提醒是确定性计算，交给规则引擎，可测试、可解释；
   AI 只做它擅长的（复盘建议、话术），并且 JSON 容错、失败不伤主功能；
2. **「死因」做成一等字段**：挂了才出现的下拉框（简历关 / 笔试挂 / 八股 / 项目深挖 / 行为面 / case / 薪资不合 / 个人放弃）——
   强制复盘的最小动作；
3. **演示数据用相对日期**：任何时候装载，提醒和漏斗都立即有内容（演示永不失效）；
4. **Kanban 而不是表格**：投递状态是流程不是属性，看板流转比改单元格更符合直觉，也顺便证明我会用产品经理的视觉语言。

## 7. 页面流程（低保真线框）

```
┌──────────────────────────────────────────────┐
│ [➕记投递][🧪演示][📋复制][⬇️下载][⚙️AI设置]   │
├──────────────────────────────────────────────┤
│ ① 漏斗：投递8→笔试3(38%)→面试3→…→Offer1(13%)  │
│    渠道进面率：内推 3/3 · 官网 1/2 · BOSS 0/3  │
├──────────────────────────────────────────────┤
│ ② 该跟进：⏰C 已投24天无下文 / B 面试停14天…   │

│ ③ Kanban：已投递｜笔试｜面试中｜终面｜HR｜Offer│
│    ｜挂了｜无回音        （卡片可流转/编辑）   │
├──────────────────────────────────────────────┤
│ ④ 死因分布：八股 2 次 · 项目深挖 1 次 …        │
└──────────────────────────────────────────────┘
```

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 提醒阈值（14/7 天）拍脑袋 | 产品说明里写明依据（投递周期行业常见节奏），欢迎反馈调整；不做「保证 HR 会理你」的承诺 |
| 手记会漏 | 不假装自动同步；演示模式 + 1 分钟成本降低坚持门槛；漏斗口径写清「按当前状态计」 |
| 统计算错 | 确定性回归评测（eval/application-board）：期望值手工算好写进用例，改代码必跑 |
| AI 输出不稳 | JSON 提取容错 + 错误原样展示；主功能完全不依赖 AI |

## 9. 里程碑

- **M1（已完成，本版本）**：P0 全部 + P1 全部 + 确定性回归评测；
- **M2（有真实使用后）**：与面试复盘器打通、死因填写率埋点、阈值可配置、日历视图评估。

## 10. 本 PRD 的局限

- 用户场景来自我自己的投递经验与同学访谈（非正式），样本小；
- 渠道进面率的「advanced」口径（非简历关死亡也算简历过了）是简化，可能与个别平台流程不符；
- 「漏斗按当前状态计」会低估曾经到达过的阶段（如面试挂了不计入「到过终面」）——取舍是口径简单可解释，M2 考虑加「最高到达阶段」字段。
