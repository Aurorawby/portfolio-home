# 内容工作台 ContentWorkbench · PRD

> 版本 v1.0 ｜ 2026-11-05 ｜ 作者：Aurorawby（AI 结对编程）
> 一句话：**内容线的全流程编排——把选题雷达的选题池变成「周计划 → 草稿 → 发布 → 数据回流」的闭环，让下周的选题比这周更聪明。**

---

## 1. 背景与问题

内容线已有三个单点工具（选题雷达 / 笔记工坊 / 排版器），但真实创作是**连续流程**，单点工具有三个摩擦：

- 选题在选题雷达里标了「待写」，写完发布后**没有任何地方记录结果**——选题策略永远得不到验证；
- 「这周该发什么」每次靠回忆重新决定；
- 发布数据（阅读/赞/藏）散在平台后台，从来没人把它和「选题类型」对起来看。

**机会**：求职线已有成功的编排先例（求职工作台把三个工具串成一条线）。内容线照此模式编排，
并把「数据回流」做成一等公民——**发布不是终点，是下一次选题的输入**。

## 2. 目标用户与场景

| 谁 | 场景 | 频率 |
|---|---|---|
| 单兵博主 | 周日打开：看周简报 → 从选题池排本周计划 → 周内起草发布 → 填数据 | 每周 1 次规划 + 每篇 1 分钟 |
| 内容运营 | 管理账号矩阵的内容排期与效果复盘 | 每周 |

## 3. 产品目标与指标

**北极星**：每周日 5 分钟内完成「看简报 → 排计划 → 知道下周多做什么」。
**正确性护栏（可测试）**：简报的漏斗统计 / 类型聚合 / 建议触发与手工计算完全一致（确定性回归）。
**信任指标**：类型建议只在样本 ≥3 时下结论——绝不拿单篇运气当规律（写进产品文案）。

## 4. 需求清单

| 级别 | 需求 | 验收标准（可测试） |
|---|---|---|
| P0 | 选题导入：读选题雷达选题池（localStorage tr_pool），排除已导入/已弃 | 同一篇不重复导入；池空时给明确指引 |
| P0 | 流水线看板：计划 → 草稿 → 已发布，卡片流转 | 流转按钮正确改状态；删除有确认 |
| P0 | 数据回流：发布卡填阅读/赞/藏/涨粉，按选题类型聚合平均阅读 | 聚合计算与手工一致（回归评测） |
| P0 | 周简报（规则引擎）：漏斗 + 警告 + 行动清单 | 5 类警告触发与手工判定一致（回归评测） |
| P0 | 统计素养约束：类型建议仅当该类型样本 ≥3 | 样本不足时输出「不下结论」文案（回归评测断言） |
| P1 | 数据回流建议：样本 ≥3 的类型中推荐均值最高者；样本不足的类型提示「先补样本」 | 文案与手工一致 |
| P1 | 周报导出 Markdown（漏斗/行动/类型表现/发布明细表） | 内容与页面一致 |
| P1 | AI 点评：基于简报客观数据的教练式点评 | 明确约束「不编造数据」；JSON 容错 |
| P1 | 演示数据：选题池 + 发布计划（含数据回流样本） | 装载后简报立即有内容且类型建议可触发 |
| P2 | 与笔记工坊自动握手（草稿状态自动点亮） | 需要笔记工坊持久化草稿，M2 |
| P2 | 多账号/多平台维度拆分表现 | 等单账号数据攒够 |

## 5. 明确不做（Not-doing）

- **不自动抓取平台数据**：阅读量手动填（平台无公开 API，爬虫碰红线），填一条 30 秒；
- **样本 <3 不给结论**：宁可说「不知道」，不给单篇运气背书的假规律；
- **不做发布排期日历**：公众号定时发布自带的够用；
- **不建账号体系**：全本地。

## 6. 关键设计决策

1. **编排而非重写**：选题生成留在选题雷达、起草留在笔记工坊——工作台只做「计划、流转、回流、简报」，
   单一职责（与求职工作台同一架构哲学）；
2. **数据回流是一等公民**：发布卡自带数据录入，这是与「纯看板」的本质区别——闭环的最后一米；
3. **统计素养写进产品**：类型建议强制样本 ≥3，不足时文案明说「均值会被单篇运气主导」；
4. **简报是代码不是模型**：警告/漏斗/行动清单是确定性计算（可测试），AI 只做口语化点评。

## 7. 页面流程（低保真线框）

```
┌────────────────────────────────────────────┐
│ ① [周起始][目标][从选题池导入▾][平台▾]       │
│    [➕加入计划]（读 tr_pool，去重）           │
├────────────────────────────────────────────┤
│ ② Kanban：📋待起草 → ✍️已起草 → 🚀已发布     │
│    已发布卡内置阅读/赞/藏/涨粉录入框          │
├────────────────────────────────────────────┤
│ ③ 数据回流：类型×平均阅读 条形 + 漏斗        │
│    「样本 ≥3 才下结论」结论卡                │
├────────────────────────────────────────────┤
│ ④ 周简报：⚠️缺草稿/缺数据 ✅好习惯 👉行动清单 │
│    [🤖AI点评] [📋复制周报]                   │
└────────────────────────────────────────────┘
```

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 跨页面数据依赖（tr_pool） | 依赖同浏览器 localStorage（与求职工作台同模式）；池空时给出「去选题雷达/装载演示」双指引 |
| 用户不填发布数据 → 回流断 | 简报把「缺数据」列为警告；填一条只要 30 秒 |
| 单篇运气被当规律 | 样本 ≥3 硬门槛写进引擎与文案 |
| 手动填数出错 | 明示「以平台后台为准」；不追求实时 |

## 9. 里程碑

- **M1（已完成，本版本）**：P0 全部 + P1 全部 + 确定性回归评测；
- **M2**：笔记工坊草稿握手、多平台拆分、第二标注人式的内容复盘（A/B 标题）。

## 10. 本 PRD 的局限

- 类型建议基于作者自标的角度标签，粒度粗；
- 「周」的边界用日期选择器约定，未做自动周切换；
- 演示数据中的阅读量为编造示例（已注明），真实结论需真实数据。

## 竞品分析（2026-11-06 补充）

> 口径：基于公开产品能力的定性对比，未做付费/深度评测。

| 替代方案 | 它强在哪 | 在我们场景里的不足 | 我们的差异 |
|---|---|---|---|
| Notion / 飞书内容日历 | 模板、协作、多端成熟 | 选题、草稿、发布数据分在不同表，数据回流要手工搬 | 选题池→周计划→草稿→数据回流一条线，同一浏览器共享 |
| 新榜 / 灰豚数据 | 平台数据、榜单成熟 | 给数据，不替你排本周计划，也不做「按选题类型」的复盘 | 周计划 + 发布漏斗 + 类型聚合 + 周简报，代码算不靠感觉 |
| Buffer / 新媒体管家 | 多平台排期/发布 | 不解决「这篇为什么表现好」的归因和样本量提醒 | 样本 <3 明确不下结论，把统计克制写进产品规则 |

**结论：** 不是又一个内容日历，而是「内容线的数据回流 + 周复盘」编排层。
